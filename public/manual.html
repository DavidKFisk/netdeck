NetDeck Manual

A plain-English guide to every part of the screen and every command in the reference — what it is, when you'd reach for it, and how to read what comes back.

Getting started

NetDeck is a reference of network and system commands that can also run them for you and show the results live. Everything runs on your own computer — nothing is sent anywhere.

Desktop app (installed)

You installed NetDeck with its installer, so there is nothing to set up: open it from the Start menu or the NetDeck icon on your desktop. The app window is the whole program — no browser, no terminal, no server to start.

  • Closing the window doesn't quit. NetDeck keeps running in the system tray (the >_ icon near the clock) so long commands carry on. Click the tray icon to bring the window back; right-click it → Quit NetDeck to stop completely.
  • The Manual and Cheat sheet open in a window of their own, so you can read and work side by side; close it whenever you like. The book icon on any card opens the manual at that command.
  • You never need a terminal or Node.js. If something asks for administrator rights, use the Run as admin button beside the STANDARD USER badge.
  • Commands you add yourself are kept in your user profile, so they survive updates. To update, run a newer installer over the top; to remove, use Settings → Apps → NetDeck.

Running from source

A small server (server.js) sits behind the web page and executes commands on your behalf. Open a terminal in the NetDeck folder and run:

node server.js

Then open http://localhost:4573 in a browser, or add --open to have it open one for you. The page and the server only talk to each other over localhost. If you were given a single netdeck.exe built with Node instead, double-clicking it does the same thing and opens the browser.

Hosted web version

You're reading this on a copy of NetDeck published to a website. A web page can't run commands on your computer, so this copy is a reference — search, playbooks as steps, the cheat sheet, pinning and links all work, but there are no run buttons. To run commands from it, pair it with a NetDeck installed on your own machine: see Hosted (web) version.

NetDeck runs on Windows, Linux and macOS. The reference is the same everywhere; on Linux or macOS the run button moves to the L/M row and runs that platform's equivalent (ip addr for ipconfig /all, ss -tulpn for netstat -ano, nc -zv for Test-NetConnection). Windows-only commands such as net view are shown for reference there.

Safe by design

Only read-only, "look but don't touch" commands can be run from the page. Commands that change settings (clearing caches, adding routes, ending processes) are shown for reference with a copy button and an orange note explaining why you'd run them yourself in a terminal.

Hosted (web) version

NetDeck can also be published to a web address as a plain reference. A web page can't run commands on your computer — browsers forbid it — so the hosted version has no run buttons, no terminal drawer and no network context. Everything else works: search, filters, playbooks (shown as steps to copy), the manual, the cheat sheet, pinning, links, and custom commands (kept in your browser).

reference mode
The note in the grey bar under the header saying commands can't run from a hosted page.
Connect local NetDeck
Turns the hosted page into the full app by pairing it with a NetDeck server running on your own computer. Start that server with the website's address as its allowed origin — the dialog shows the exact command — and it prints a pairing token; enter the address (http://localhost:4573) and the token, click Test & connect, and run buttons, the terminal and the health strip appear. The server only ever accepts that one website, only with the token, and still listens on your own machine only. Works in Chrome, Edge and Firefox; Safari blocks web pages from reaching localhost.

Network context strip

The dark bar under the header shows what NetDeck detected about this computer's connection when the page loaded. It exists so you don't have to remember your own addresses — every host box on the page gets one-click chips built from these values.

HOST
Your computer's name on the network.
ADAPTER
The network connection currently carrying your internet traffic — usually Wi-Fi or Ethernet. If you have several, NetDeck picks the one that actually has a working address.
IP
Your computer's address on the local network, e.g. 192.168.7.45. Other devices in your home or office reach you at this address.
GATEWAY
The address of your router — the device that connects your local network to the internet. Almost always ends in .1 or .254. If the gateway doesn't answer a ping, nothing beyond your own network will work.
DNS
The servers that turn names like google.com into addresses. Often the router itself, or your internet provider's servers.
GATEWAY PING / INTERNET PING
Two tiny live charts. Every 10 seconds NetDeck pings your router and Cloudflare's 1.1.1.1 once and plots the reply time, so a problem shows up before you go looking for it. The number beside each is the latest reply: green is normal, amber is slow (over 50 ms to the router, over 100 ms to the internet), red is very slow or no reply at all; a red tick in the chart marks a missed reply. A steady low line is what healthy looks like; a line that climbs when you start a download is congestion; gaps are drop-outs. Hover for the max over the last few minutes.
STANDARD USER / ADMIN
Whether NetDeck was started from an elevated ("Run as administrator") shell. A few command variants only work when elevated — netstat -anob, which lists the program behind each connection, is the main one. Those variants are shown as "admin only (locked)" until NetDeck runs as administrator. Everything else works either way.
Run as admin
Appears beside the badge whenever NetDeck is not elevated. In the desktop app it restarts NetDeck with administrator rights: NetDeck closes, Windows shows its usual permission prompt, and NetDeck reopens with the badge reading ADMIN. Anything still running stops and open tabs close; your history, pins and custom commands are kept. If you decline the Windows prompt, NetDeck just reopens as it was. It lasts until you quit — the next normal start is un-elevated again. (If Windows asks for another account's password because yours isn't an administrator, NetDeck runs as that account and shows that account's history and pins.) In the run-from-source edition the button is labelled How to run as admin and shows the exact commands for that installation's folder, since a web page can't restart its own server.
↻ (refresh)
Re-detects everything. Use it after switching from Wi-Fi to a cable, connecting a VPN, or fixing a network problem.
If the IP starts with 169.254

That is an "APIPA" address — Windows made it up because no router handed out a real one. It means DHCP failed: check the cable or Wi-Fi connection, then try ipconfig /release followed by ipconfig /renew in a terminal.

The terminal drawer

The dark panel pinned to the bottom of the window. It stays collapsed to a thin bar until you run something, then opens to show the output. Each run gets its own tab, so a slow command keeps going while you start another.

Tab strip
One tab per run, named after the command. Click to switch; click × to close (this also stops the command if it's still running). The active tab has a green underline.
status dot
Pulsing green: running. Solid green: finished normally. Amber: finished but reported a problem (for example, ping got no replies). Red: couldn't run at all. Grey: you stopped it.

The line at the top of each tab: what ran, when it started, how long it has been running (it counts up live), and its exit code. exit 0 means "completed without error"; anything else means the program is reporting a failure — for ping, exit 1 simply means the host didn't reply.

On the right of that line. Type to highlight every match in the output and see the count; Enter jumps to the next match, Shift+Enter to the previous, Esc clears. Works while a command is still running.

Toggles line wrapping. Off shows long lines (like route print or wide PowerShell tables) on one line with a horizontal scroll, which keeps columns aligned. The setting is remembered.

Downloads the tab's output as a .txt file named after the command and time, with the command line and timestamp at the top — for attaching to a ticket or comparing later.

Stop
Ends the running command in the active tab. Use it for long ones like pathping or tracert to a host that isn't answering.
Copy
Copies the whole output of the active tab. For a playbook, it copies the step-by-step summary and the verdict.

Table view

Raw command output is designed for the 1990s. For the commands where it matters, NetDeck turns it into a real table:

  • Click a column header to sort; click again to reverse. Numbers sort as numbers.
  • Filter rows… keeps only rows containing what you type — type 443 to see everything on port 443, or LISTENING to see only open ports.
  • The row count on the right shows how many rows match.
  • For netstat -ano and Get-NetTCPConnection, NetDeck adds a Process column by looking up each PID — so instead of "PID 21920 is on port 80" you see "com.docker.backend.exe is on port 80".

Commands with a table view: netstat -ano, arp -a, route print, ipconfig /all, ipconfig /displaydns, tasklist, getmac, Get-NetTCPConnection, Resolve-DnsName.

History

Every finished run is remembered — the last 30, output included — in your browser, so it survives closing the page or restarting the server. Open it with the History button.

Row
Status dot, the command, and when it ran / how long it took / its result. Click the row to reopen the output in a new tab.
↻
Runs that exact command again, with the same host and port.
Clear
Forgets everything in the history. (Close all does not do this.)

Working with results

Four tools on the output bar and in each tab turn a run into evidence you can keep, compare and hand over.

note
On the right of a run's top line (and on the bar above a playbook's steps). Opens a box for a note about this run — what you were seeing, a ticket number, what you tried. The note is saved with the run in History (a ✎ marks entries that have one; hover to read it) and goes into any report you save. It is yours alone; nothing is sent anywhere.
Compare
With a finished run in front of you, press Compare and pick an earlier run of the same command or playbook — an open tab or a History entry. NetDeck opens a new tab showing the difference line by line: lines only in the older run in red, only in the newer in green, unchanged stretches folded. For playbooks it compares the step summaries and the verdict. This is the "what changed since it worked?" question answered in one click; run ipconfig /all, route print or the network scan when things work, and compare when they do not.
Report
Saves the run in front of you as a single HTML file: title, time, your note, the output and its table for a command, the steps (with their full output in collapsible sections) and the verdict for a playbook. It opens in any browser and has a Print / save as PDF button. Anonymise is on by default: your computer's name becomes OFFICE-PC, every address is replaced consistently (private ones with 192.0.2.x, public with 203.0.113.x — so the same device keeps the same fake address throughout), and the device half of MAC addresses becomes xx-xx-xx. Well-known addresses such as 1.1.1.1 are left alone. Turn it off for a report you keep yourself.
Schedule
Runs a playbook every 5 minutes to 3 hours while NetDeck is open — Scan my network every 15 minutes, say, or Does my connection drop out? every hour. Each run opens a tab; an unchanged run replaces the previous one so tabs do not pile up. A run whose result changed — a new device, a verdict that flipped, a step that started failing — is kept, marked with "!" in its tab, counted on the ⏱ badge in the context strip, and (if you tick "notify on change") announced with a desktop notification. Schedules are remembered and resume when NetDeck is reopened; they never run while it is closed. Playbooks that need input appear in the list once you have run them, with the input you used last.

Playbooks

A playbook is a set of commands run in a sensible order, each one checked automatically, ending in a one-paragraph verdict. They exist because real troubleshooting is a sequence — "can I reach my router? then the internet? then can I look up names?" — and doing it by hand means running five commands and squinting at each.

There are twenty-five, arranged in four groups. Connectivity: can't reach the internet, a website won't load, everything is slow, does it drop out, are packets being dropped, where the path breaks, is a port open, service sweep, MTU, Wi-Fi health. DNS & email: DNS health, DNS propagation, email delivery. Security & exposure: what this PC exposes, who it's talking to, is my DNS honest, router check-up, proxy and HTTPS inspection. This PC & local network: scan my network, PC health, clock, routing and adapters, DHCP and address conflicts, who's on my network, IPv6. Pinned playbooks move to the front of their group.

While a playbook runs, each step shows a symbol and a summary:

○ pending
Hasn't started yet.
● running
In progress — output is streaming in behind the output button.
✓ pass
The check succeeded. The summary shows the key numbers (e.g. "4/4 replies, avg 12 ms").
! warn
It worked, but not cleanly — packet loss, or a service that isn't advertising.
✕ fail
The check failed. The summary says how.
i info
Worth reading, but not a fault — for example "Windows network browsing is switched off here", which is normal on Windows 10/11.
– skipped
Shown greyed out. not needed: the step only runs when an earlier result calls for it (you gave an IP address, so no name lookup; ping worked, so no TCP fallback). not run: an earlier step failed in a way that makes the rest pointless — no IP address means there's nothing to test — so the playbook stops rather than making you wait through a minute of timeouts. not detected: it needed something NetDeck couldn't find, such as a gateway. Steps marked with a ? on the playbook card are these conditional ones.
output
Click to see the raw text of that step, exactly as the command printed it. Hover a finished step to see how long it took.
table
Appears on steps whose output NetDeck can parse (the adapter check, the ARP cache). Opens the same sortable, filterable table you get from the Table button on a normal run, right inside the step.

The verdict box at the bottom is green (all clear), amber (attention), or red (problem found), and always says what to do next. When the next thing is obvious it offers buttons: run the playbook that narrows the problem down, or copy the fix-it command (such as ipconfig /flushdns) ready to paste into a terminal. Those commands change settings, so NetDeck copies them rather than running them.

Can't reach the internet?

The one to start with when "the internet is down". It walks the chain outward from your computer and stops at the first broken link:

  1. Check your adapter — does the adapter you're actually using (the one in the context strip) have a real address and a gateway? It ignores virtual adapters from Docker, Hyper-V or a VPN, which otherwise hide a dead connection. A failure here stops the run (cable / Wi-Fi / DHCP problem). It also warns if a second adapter has a default route but no valid address, which can quietly capture your traffic.
  2. Ping the router — does it answer, and quickly? Over 50 ms or any lost packets is flagged: on Wi-Fi that means weak signal or interference.
  3. Ping the internet at 1.1.1.1 — does anything past the router answer?
  4. TCP to 1.1.1.1 (only if that ping failed) — many office networks block ping, so before blaming your provider it tries a real connection. If this works, you're online and ping is simply blocked.
  5. Resolve example.com — do names still work? (fail → DNS problem; the verdict offers to run the DNS playbook)
  6. Look for a sign-in portal — fetches Microsoft's connectivity test page. A redirect or a different page means hotel/café/guest Wi-Fi is waiting for you to sign in.
  7. HTTPS to example.com — can you actually open a secure connection? (fail → firewall, proxy or security software)

Is a port open on a host?

Give it a host and a port (say github.com and 443). It resolves the name, pings the host, then tries the port. The point is telling apart situations that look identical in a browser:

  • The name doesn't exist — the run stops there.
  • Refused — the connection is rejected within a few seconds. The machine is up and said "no": nothing is listening on that port (service stopped, or it's on a different port).
  • Filtered — no response at all until the ~20-second timeout. A firewall is silently dropping the connection.
  • Nothing answers — neither ping nor the port. Only then does it run a quick route trace to show where the path stops: inside your own network, in your provider's, or beyond.

Is DNS healthy?

Looks up the same name through your configured DNS server, your second configured server if you have one (a dead backup server causes random multi-second stalls), then Cloudflare (1.1.1.1) and Google (8.8.8.8) — timing each answer. If yours fails and the public ones work, your router or provider's DNS is the culprit and the verdict tells you to switch. If they all fail, it's not DNS at all — you have no connectivity, and the verdict offers the internet playbook.

The last step asks for a name that cannot exist (it ends in .invalid). An honest resolver says "no such name"; if an address comes back, something — your provider's search page, a captive portal, a filtering product — is rewriting DNS answers. A lookup that succeeds only after a first attempt timed out is reported as slow, not broken.

Scan my network

Two steps now. First it asks devices to announce themselves over mDNS/Bonjour and UPnP, which is how TVs, speakers, printers, Apple and Google devices give their real names. Then it pings every address in your subnet at once and reads the ARP table. The table gains three things: the Name column fills from what devices said about themselves, a Seen column says when NetDeck first saw each device (NEW means never before), and every row has a probe button that runs the port probe on that address to ask what it is. The verdict adds what changed since the previous scan — new devices, devices that have gone, and devices that changed address — because NetDeck now remembers each scan (in this browser or app only; nothing leaves the PC). A new device turns the verdict amber so it is not missed.

NetDeck's IP scanner: it finds every device on your network, not just the ones this PC has talked to. There is nothing to type — it works out your subnet from your own address, pings all of its addresses at the same time (so 254 addresses take about six seconds, not four minutes), then reads the ARP table the sweep has just filled. That second step matters: phones, TVs and smart-home gadgets often ignore ping, but they cannot avoid answering ARP, so they still show up — marked no reply in the Ping column.

Press table for the full list: IP address, name (when the network can supply one — on home networks it usually can't), MAC address, manufacturer, whether it answered ping, and a note marking this PC and the router. Sort by Manufacturer to group things: five Wyze cameras, three eero units and so on. Two values in that column deserve explanation:

  • private address (randomised) — phones, tablets and recent laptops invent a random MAC address for each Wi-Fi network, for privacy. It belongs to no manufacturer, so it can't be identified this way. Usually these are your family's phones.
  • blank — the prefix is not in the IEEE registry NetDeck carries (the official list of every manufacturer's address blocks, about 54,000 entries, bundled with the app). That is rare for real hardware: it usually means a virtual adapter, a device faking its address, or a very new assignment — the registry is refreshed with each NetDeck release.

Anything you can't account for is worth tracking down; your router's own client list usually shows a name for each address. What it will not do: it only ever scans the private subnet this PC is on, never more than 254 addresses, and refuses to run on a public address — it's a "what's on my network" tool, not a general scanner. Reply times aren't shown, because pinging 254 addresses at once makes them meaningless; use ping on one device for that.

Who's on my network?

Pings your router to freshen the cache, then reads the ARP cache (every device your computer has recently exchanged packets with), counting real devices on your network and ignoring broadcast and multicast entries. Press table on that step to see each device's IP and MAC address. The cache only knows devices you've exchanged traffic with, so quiet ones can be missing.

A website won't load

The most common complaint, and the hardest to untangle by hand. Give it the site (you can paste a whole address — it keeps just the host). It resolves the name with your DNS and with a public one, connects to port 443, asks for the page headers, times each phase of a real request, and — only if something failed — loads a known-good control site so it can tell "it's them" from "it's you". Possible verdicts:

  • Your DNS can't resolve it but public DNS can — stale cache, filtering, or a blocked name; offers the DNS playbook and the flush command.
  • The name doesn't exist — a typo, or the domain lapsed.
  • The site refuses or drops connections while the control site loads — it's at their end (or they are blocking you).
  • Nothing loads, control included — it's your connection; offers the internet playbook.
  • The secure connection fails — certificate or TLS error. Check this PC's clock first, then security software or a proxy.
  • HTTP 5xx — their server is erroring. 403 / 404 — the site is up; that page or your access is the issue.
  • It loads, slowly — and says which phase ate the time: looking up the name, reaching the server, setting up encryption, waiting for the server to build the page, or downloading.

Why is everything slow?

Twenty pings to your router and twenty to the internet — reporting average, worst case, jitter (how much the delay wobbles) and loss — then a timed DNS lookup and a timed web request, and the Wi-Fi link if you're on wireless. Takes about a minute. The logic is simple: if the numbers to your router are bad (a healthy link is 1–5 ms with almost no jitter), the problem is between this PC and the router — Wi-Fi signal, interference, a cable. If the router is clean but the internet numbers are bad, it's your provider or a saturated connection, and the verdict offers to trace the path. If both are clean it checks whether DNS or the web server was the slow part.

Windows 11 and Wi-Fi details

Windows now hides Wi-Fi signal information from programs unless Location services are on (Settings → Privacy & security → Location) or the program runs as administrator. When that happens the Wi-Fi step says so and the rest of the playbook still works.

Does my connection drop out?

The three-minute version of the stability monitor, with a verdict: one ping a second to your router and to the internet, a line every ten seconds, runs of loss called out as they happen. Start it when the problem tends to happen and keep working; it needs no input and no admin rights. The verdict says whether dropouts are on the local link (router pings lost — Wi-Fi, cable, adapter, router), beyond the router (only internet pings lost — the ISP), or whether there is no loss but the delay wobbles (jitter, which calls and games feel). If three minutes is not enough to catch it, run the monitor command's 10-minute variant instead.

Are packets being dropped on this PC?

The playbook behind the packet counters: for ten seconds it counts packets on every layer of this PC's network stack — the adapter, and the firewall, VPN and other filter drivers stacked on it — while it pings your router and the internet once a second and downloads a 5 MB test file from Cloudflare. Everything is measured in the same ten seconds, so the verdict can line the two up. It needs administrator rights (press Run as admin first; otherwise it just tells you so).

How to read the verdict:

  • Nothing dropped, every ping answered, download clean — there is no packet loss on this PC. If something still feels wrong, it's speed or something further away: try Why is everything slow? or Where does the path break?.
  • Drops on a Filter layer — software on this PC threw packets away. "WFP" is the Windows Filtering Platform, i.e. the firewall or a security product; a VPN's own driver shows under its name. A handful is normal (unsolicited inbound traffic and discovery chatter that the firewall is meant to block); hundreds during a stalled transfer are not.
  • Drops on the NIC row — the adapter or the link itself: Wi-Fi signal, a cable, a driver.
  • Router pings lost, nothing dropped here — packets left this PC cleanly and the router didn't answer: the problem is the link to the router.
  • Only internet pings lost — the loss is beyond your router.

Where does the path break?

Runs a route trace (up to 20 hops) and reads it for you. It reports whether the destination was actually reached — tracert prints "Trace complete" even when the last hops never answered — where replies stop, and where latency steps up and stays up (one router replying slowly is normal and ignored). Each hop is labelled as your network, your provider's access network, or the internet, so "hop 2" becomes "the link to your provider". Press table for the hop list. Some hosts never answer traces; if the site works in a browser, a trace that goes quiet near the end means only that.

What is this PC exposing?

Lists every TCP port this machine is listening on with the program behind it, split into reachable from the network (listening on all addresses) and local only (127.0.0.1, invisible to other machines). It flags remote-access and database services — Remote Desktop, VNC, Telnet, FTP, SQL Server, MySQL, PostgreSQL, Redis, MongoDB, the Docker API — which are the ones worth being sure about, and checks that Windows Firewall is on for every profile. Ports 135, 139 and 445 are standard Windows services, and the block of high ports (49152 and up) are Windows' own; both are summarised rather than listed one by one. "Reachable" means a program is listening; whether the firewall lets outsiders in depends on its rules.

Routing & adapter sanity

For "it works on Wi-Fi until I plug the cable in", half-connected VPNs, and connections that die for no visible reason. It reads the routing table for default routes — the "send everything else this way" rules. One is normal. Several means adapters are competing, and the lowest metric wins; the verdict lists them with the winner marked ▶. The dangerous case is an adapter that holds a default route but has no valid address (cable plugged in, DHCP failed): if it wins, your traffic goes nowhere. It also lists which DNS servers each adapter uses — a VPN adapter often takes DNS priority, which is why lookups may go to a server you don't recognise.

Did my DNS change propagate?

For when you've changed a DNS record and want to know who sees it yet. It finds the domain's authoritative nameservers (looking in the parent zone if you gave a host like www.example.com), asks them directly — that's the truth — and compares the answers from your resolver, Cloudflare, Google and Quad9. Resolvers that differ are serving a cached copy that updates when the old record's TTL expires; nothing to fix, just wait (or flush your own cache). If the two authoritative servers disagree with each other, the zone hasn't synchronised at your DNS host, which is worth fixing first.

Large sites rotate or geo-balance their addresses, so every query gets a different answer. The playbook detects this by asking the same authoritative server twice; when it sees rotation it compares network ranges instead of exact addresses, and says so.

Wi-Fi health

Reads your wireless link — signal strength, band (2.4 or 5 GHz), radio mode, link rate — then surveys nearby access points to count how many strong ones share or overlap your channel, and sends twenty pings to the router to see how steady the link really is. Flags weak signal (under 55%), the crowded 2.4 GHz band, old radio modes and low link rates; on 2.4 GHz it suggests the quietest of channels 1, 6 and 11. On Windows 11 the first two steps need Location services on (or an administrator shell); without that the ping test still tells you whether the link is steady.

Can I reach that service?

Give it one host. It checks the name and ping, then tries the common service ports in a single run — HTTPS 443, HTTP 80, SSH 22, Remote Desktop 3389, SMB file sharing 445, SQL Server 1433 — and lists each as open, refused (the machine is up, nothing is listening) or filtered (a firewall drops it). If the host answers neither ping nor the web ports it stops early rather than waiting out every timeout. This is a small port sweep: use it on machines you're responsible for.

MTU check — "some sites hang"

Every network path has a largest packet size, its MTU (Maximum Transmission Unit) — normally 1500 bytes; less over PPPoE, VPNs and tunnels. It sends pings marked "don't fragment" at decreasing sizes and stops at the first that gets through; that size plus 28 bytes of headers is your path MTU. A smaller MTU is fine as long as the "packet too big" messages reach you. When a firewall blocks them, small transfers work and large ones silently stall: pages half-load, uploads hang, VPNs feel flaky. The verdict gives the number to set on the adapter or VPN if you have those symptoms.

Email delivery check

Give it a domain (the part after the @). It looks up the MX records (which servers receive its mail), checks for an SPF record (which servers may send as this domain) and a DMARC record (what receivers should do with forgeries) — missing ones are the usual reason legitimate mail lands in spam — and tries port 25 on the first mail server. Expect that last step to fail on home and most office connections: providers block outbound port 25, and mail programs use 587 or 465 instead. The verdict says so rather than calling it a fault.

PC health snapshot

The quick triage for "my computer is slow", no networking involved: days since the last restart (over two weeks is flagged), memory in use (over 90%), free space on each drive (under 10% warns, under 5% fails — Windows slows down and updates fail), programs that are "Not responding", the five biggest memory users with their process counts, and how long ago Windows last installed an update (over 60 days suggests Windows Update is stuck).

Clock & time sync

Measures your clock against time.windows.com. Within a second is healthy. A clock that is minutes out breaks things that seem unrelated: every HTTPS site shows certificate errors (certificates look expired or not yet valid), and logins to work accounts fail (Kerberos allows five minutes). The second step shows where the clock syncs from; on a home PC the Windows Time service is usually idle between scheduled syncs, which is normal. If the clock keeps drifting back, the motherboard battery may be failing.

Who is this PC talking to?

Every live outbound connection, grouped by program: how many connections each has, and to which ports. Ports 80 and 443 are ordinary web traffic; anything else is listed so you can recognise it. Press table for each connection with its remote address. Useful for "what's using my connection right now?" and for noticing a program you don't recognise phoning home.

DHCP lease & address conflicts

Shows whether your address is leased or typed in by hand, which DHCP server issued it and how long is left (Windows renews at the halfway point, so a few hours left is normal), whether that server still answers, and whether Windows has logged another device using your IP address. A recent conflict explains connections that drop at random: two devices with one address knock each other offline. An event from more than a month ago is reported as history, not a fault.

Is my DNS honest?

Two steps: the DNS honesty check (who answers your lookups, tampering and interception tests, VPN leak, encryption) and the hosts file & DNS cache audit (redirections on this PC itself). The verdict names the one thing that matters: a hosts-file hijack (scan the PC), a tampering resolver (switch it — the verdict offers the command to copy), interception on this network (use encrypted DNS), a VPN leak (set the VPN's DNS), or honest-but-unencrypted (optional: encrypt it). No input, no admin.

Router check-up

The router check-up with a verdict: telnet open is a fail, UPnP forwards or TR-069 are worth knowing about, otherwise healthy — with a reminder of the two things it cannot check for you, firmware and the admin password. Only ever your own gateway; read-only.

Proxy & HTTPS inspection

Shows any proxy configured system-wide or for your account, then connects to a well-known site and reads the certificate it presents to you. Normally that's signed by a public certificate authority. If it's signed by a security product instead — Zscaler, Fortinet, Sophos, an antivirus "web shield" — your HTTPS traffic is being decrypted and re-signed on the way. On a work PC that's usually policy; on a personal one it's worth knowing about.

IPv6 check

Most networks are fine either with working IPv6 or with none. The troublesome case is half-working IPv6: you have a global address but nothing is reachable over it, so programs try IPv6 first, wait for it to fail, and only then fall back — sites hesitate for seconds. The playbook checks for a global address (link-local fe80:: and private fd… addresses, such as a VPN assigns, don't count), and if there is one, pings and loads an IPv6-only site.

The most basic question in networking: "are you there?" It sends four small packets to the host and waits for echoes. The reply time (latency) tells you how far away the host is in network terms; missing replies tell you something in between is dropping packets.

Address resolution (ARP)

On your local network, computers find each other by MAC address, not IP. The ARP cache is your computer's memory of "IP → MAC" for every device it has talked to recently. Reading it is the quickest way to see what's on your network, and to spot two devices claiming the same IP.

Interface: 192.168.7.45 --- 0x5
  Internet Address      Physical Address      Type
  192.168.7.1           f8-bb-bf-00-11-22     dynamic    ← router
  192.168.7.23          e4-c7-67-00-33-44     dynamic
  192.168.7.26          98-7a-9b-00-55-66     dynamic

ssh · scp · sftp ALL copy only

Secure remote access. ssh user@host gives you a terminal on another machine; scp file user@host:/path copies a file to it; sftp user@host is an interactive file browser. All three are built into Windows 10/11 now. They need a live keyboard session, so open a terminal for them.

whois <domain> ALL copy only

Looks up who registered a domain name (or who owns an IP address block), when it expires, and which name servers it uses. Not included with Windows; Microsoft's Sysinternals suite has one, and any Linux/macOS machine has it built in.

iperf3 ALL runnable

The definitive throughput test between two machines you control — it measures the raw speed of the network path with no website or disk in the way, which is how you find out whether "the Wi-Fi is slow" or "the internet is slow". One machine runs iperf3 -s (the server); this PC connects to it and pushes data for 10 seconds. Variants: reverse (the server sends, this PC receives — the download direction), 4 parallel streams (a single stream cannot always fill a fast link), and be the server for one test from another machine. iperf3 must be installed on both ends; NetDeck says so plainly if it is missing here.

[ ID] Interval           Transfer     Bitrate
[  5]   0.00-1.00   sec  112 MBytes   940 Mbits/sec
…
[  5]   0.00-10.00  sec  1.09 GBytes   938 Mbits/sec   sender
[  5]   0.00-10.00  sec  1.09 GBytes   937 Mbits/sec   receiver

Glossary

IP address
A device's number on a network, like 192.168.7.45. Addresses starting with 10., 172.16–31. or 192.168. are private (only meaningful inside your network); anything else is a public internet address.
MAC address
The hardware serial number of a network card, like a4-6b-b6-12-34-56. Fixed for life; only used within your local network.
MTU
Maximum Transmission Unit — the largest packet, in bytes, a connection carries in one piece. 1500 on ordinary Ethernet and Wi-Fi; smaller over VPNs and PPPoE. When a path's MTU is lower than your PC assumes, big packets vanish and some sites load partway then hang.
Gateway / router
The device that forwards traffic between your local network and the internet. Its address is the "Default Gateway" in ipconfig.
DNS
Domain Name System — the service that converts names (github.com) into IP addresses. When DNS is down, "the internet is down" even though the connection is fine.
DHCP
The service (usually on the router) that hands out IP addresses automatically. A "lease" is the address you were given and how long you may keep it.
APIPA / 169.254.x.x
The made-up address Windows assigns itself when DHCP doesn't answer. Seeing it means "I'm not really connected".
Subnet mask
Defines which addresses count as "local". With 255.255.255.0, everything sharing your first three numbers is on your network; anything else goes via the gateway.
Port
A numbered door on a computer, 1–65535, each used by one program. Web is 80/443, SSH 22, Remote Desktop 3389. "Listening" means a program is waiting at that door.
TCP / UDP
The two ways to send data. TCP checks everything arrived (web, email, file transfer); UDP just sends and hopes (video, DNS lookups, games).
Latency / ms
How long a packet takes to get there and back, in milliseconds. Lower is better; under 20 ms feels instant.
Packet loss
Percentage of packets that never arrived. Anything above 1–2% makes calls choppy and pages stall.
TTL
Time To Live. In ping, roughly how many routers the reply passed through (starts at 64 or 128 and counts down). In DNS, how many seconds an answer may be cached.
ARP
Address Resolution Protocol — how devices on the same network learn each other's MAC addresses. The "ARP cache" is the resulting IP→MAC list.
PID
Process ID — the number Windows gives each running program. netstat shows PIDs; tasklist turns them into names.
Localhost / 127.0.0.1
Your own computer, from its own point of view. Pinging it tests only that networking software is alive, not any connection.
Exit code
The number a program reports when it finishes. 0 means success; anything else is a program-specific error. NetDeck shows it at the top of each tab.
Elevated / admin
A program started with "Run as administrator", after Windows' permission prompt. Some commands (netstat -b, arp -d, sfc) only work that way. Being logged in as an administrator is not the same thing: programs still start un-elevated until you approve that prompt.
NetBIOS
The old Windows naming system behind file sharing and \\COMPUTER\share paths. nbtstat speaks it.
