NetDeck Manual

A plain-English guide to every part of the screen and every command in the reference — what it is, when you'd reach for it, and how to read what comes back.

Getting started

NetDeck is a reference of network and system commands that can also run them for you and show the results live. Everything runs on your own computer — nothing is sent anywhere.

Desktop app (installed)

You installed NetDeck with its installer, so there is nothing to set up: open it from the Start menu or the NetDeck icon on your desktop. The app window is the whole program — no browser, no terminal, no server to start.

  • Closing the window doesn't quit. NetDeck keeps running in the system tray (the >_ icon near the clock) so long commands carry on. Click the tray icon to bring the window back; right-click it → Quit NetDeck to stop completely.
  • The tray light. The tray icon doubles as a connection light: a small dot on it turns green when the connection is fine, amber when it is unsteady (internet over 150 ms, router over 60 ms, or a ping lost in the last minute) and red when the internet has been down for about 10 seconds or this PC has no network at all. Hover over it for the latest router and internet ping, or how long the internet has been down and on which side of the router. It checks every 5 seconds while NetDeck runs, even with the window closed to the tray. Turn it off or on with Connection status in tray in the tray menu, or Tray light on the Network sensors card.
  • Mini monitor. Right-click the tray icon → Mini monitor (or Pop out on the Network sensors card) for a small always-on-top window with the live ping or traffic graph.
  • Start with Windows. Right-click the tray icon → Start with Windows (or use the button on the Dashboard's Outage log card) and NetDeck opens hidden in the tray each time you sign in — handy for the outage log and scheduled playbooks. It needs no administrator rights, shows up in Task Manager's Startup apps as NetDeck, and is removed again when you uninstall.
  • The Manual and Cheat sheet open in a window of their own, so you can read and work side by side; close it whenever you like. The book icon on any card opens the manual at that command.
  • You never need a terminal or Node.js. If something asks for administrator rights, use the Run as admin button beside the STANDARD USER badge.
  • Commands you add yourself are kept in your user profile, so they survive updates. To update, run a newer installer over the top; to remove, use Settings → Apps → NetDeck.
  • Two installers. NetDeck_1.33.1_x64-setup.exe is the everyday one (about 5 MB). The app draws its window with Microsoft Edge WebView2, which Windows 11 and up-to-date Windows 10 already have; on a PC without it, this installer downloads it from Microsoft. NetDeck_1.33.1_x64-offline-setup.exe (about 210 MB) carries WebView2 inside, so it installs with no internet at all — use it on air-gapped machines, or on a PC whose network is the thing you are trying to fix. Both install the same app.

Running from source

A small server (server.js) sits behind the web page and executes commands on your behalf. Open a terminal in the NetDeck folder and run:

node server.js

Then open http://localhost:4573 in a browser, or add --open to have it open one for you. The page and the server only talk to each other over localhost. If you were given a single netdeck.exe built with Node instead, double-clicking it does the same thing and opens the browser.

Hosted web version

You're reading this on a copy of NetDeck published to a website. A web page can't run commands on your computer, so this copy is a reference — search, playbooks as steps, the cheat sheet, pinning and links all work, but there are no run buttons. To run commands from it, pair it with a NetDeck installed on your own machine: see Hosted (web) version.

NetDeck runs on Windows, Linux and macOS. The reference is the same everywhere; on Linux or macOS the run button moves to the L/M row and runs that platform's equivalent (ip addr for ipconfig /all, ss -tulpn for netstat -ano, nc -zv for Test-NetConnection). Windows-only commands such as net view are shown for reference there.

Addresses in this manual are examples

Every address you see here is a placeholder, not a real network: 192.168.1.x stands for your own local network (yours may be 192.168.0.x, 10.x.x.x or something else — the context strip shows the real one), 203.0.113.x for a public address that is not a named service, and 10.0.0.x for a network in front of yours. Screenshots are taken from a real network and then anonymized the same way: the computer name becomes OFFICE-PC, local addresses are renumbered into 192.168.1.x, public ones into 203.0.113.x, and the device half of every MAC address is hidden.

Safe by design

Only read-only, "look but don't touch" commands can be run from the page. Commands that change settings (clearing caches, adding routes, ending processes) are shown for reference with a copy button and an orange note explaining why you'd run them yourself in a terminal.

Hosted (web) version

NetDeck can also be published to a web address as a plain reference. A web page can't run commands on your computer — browsers forbid it — so the hosted version has no run buttons, no terminal drawer and no network context. Everything else works: search, filters, playbooks (shown as steps to copy), the manual, the cheat sheet, pinning, links, and custom commands (kept in your browser).

reference mode
The note in the gray bar under the header saying commands can't run from a hosted page.
Connect local NetDeck
Turns the hosted page into the full app by pairing it with a NetDeck server running on your own computer. Start that server with the website's address as its allowed origin — the dialog shows the exact command — and it prints a pairing token; enter the address (http://localhost:4573) and the token, click Test & connect, and run buttons, the terminal and the health strip appear. The server only ever accepts that one website, only with the token, and still listens on your own machine only. Works in Chrome, Edge and Firefox; Safari blocks web pages from reaching localhost.
Disconnect
Forgets the pairing and returns to reference mode.

Network context strip

The dark bar under the header shows what NetDeck detected about this computer's connection when the page loaded. It exists so you don't have to remember your own addresses — every host box on the page gets one-click chips built from these values.

HOST
Your computer's name on the network.
ADAPTER
The network connection currently carrying your internet traffic — usually Wi-Fi or Ethernet. If you have several, NetDeck picks the one that actually has a working address.
IP
Your computer's address on the local network, e.g. 192.168.1.45. Other devices in your home or office reach you at this address.
GATEWAY
The address of your router — the device that connects your local network to the internet. Almost always ends in .1 or .254. If the gateway doesn't answer a ping, nothing beyond your own network will work.
DNS
The servers that turn names like google.com into addresses. Often the router itself, or your internet provider's servers.
GATEWAY PING / INTERNET PING
Two tiny live charts. Every 10 seconds NetDeck pings your router and Cloudflare's 1.1.1.1 once and plots the reply time, so a problem shows up before you go looking for it. The number beside each is the latest reply: green is normal, amber is slow (over 50 ms to the router, over 100 ms to the internet), red is very slow or no reply at all; a red tick in the chart marks a missed reply. A steady low line is what healthy looks like; a line that climbs when you start a download is congestion; gaps are drop-outs. Hover for the max over the last few minutes.
STANDARD USER / ADMIN
Whether NetDeck was started from an elevated ("Run as administrator") shell. A few command variants only work when elevated — netstat -anob, which lists the program behind each connection, is the main one. Those variants are shown as "admin only (locked)" until NetDeck runs as administrator. Everything else works either way.
Run as admin
Appears beside the badge whenever NetDeck is not elevated. In the desktop app it restarts NetDeck with administrator rights: NetDeck closes, Windows shows its usual permission prompt, and NetDeck reopens with the badge reading ADMIN. Anything still running stops and open tabs close; your history, pins and custom commands are kept. If you decline the Windows prompt, NetDeck just reopens as it was. It lasts until you quit — the next normal start is un-elevated again. (If Windows asks for another account's password because yours isn't an administrator, NetDeck runs as that account and shows that account's history and pins.) In the run-from-source edition the button is labeled How to run as admin and shows the exact commands for that installation's folder, since a web page can't restart its own server.
↻ (refresh)
Re-detects everything. Use it after switching from Wi-Fi to a cable, connecting a VPN, or fixing a network problem.
If the IP starts with 169.254

That is an "APIPA" address — Windows made it up because no router handed out a real one. It means DHCP failed: check the cable or Wi-Fi connection, then try ipconfig /release followed by ipconfig /renew in a terminal.

Views & filters

Commands / Playbooks / Dashboard
Three views. Commands is the reference — one card per command. Playbooks are guided, multi-step diagnostics that run several commands in order and give you a verdict (see Playbooks). Dashboard is one screen that says how the network is right now (see Dashboard). Typing in the search box while on the dashboard switches to Commands.
All platforms · Windows · PowerShell · Linux / macOS
Show only commands that exist on that platform. "Linux / macOS" shows every card that has an L/M row.
Category chips (dashed)
Narrow the list to one topic — DNS, ports, routing, and so on. "★ pinned" shows only the cards you've pinned. Combine with the search box and platform chips; the "N of 60 commands" line tells you how many match.
Playbook groups
In the Playbooks view the chips change to the four playbook groups — Connectivity, DNS & email, Security & exposure, This PC & local network — plus "★ pinned". The playbooks are laid out under those headings, and the same search box now filters playbooks: it looks at the name, the description and the commands each one runs, so typing a symptom ("slow", "certificate", "port 25") or a command (tracert) both work.
+ Add command
Adds your own command to the reference: a name, what it's for, a category, the Windows and/or Linux/macOS syntax and an optional note. It becomes a normal card with copy buttons and appears in search, the palette and the cheat sheet. Custom commands are reference-only — they never get a run button, because only the built-in, vetted list can execute. They're saved in custom-commands.json next to the app (or in your browser, on the hosted version).

Copies that row's command text to your clipboard, ready to paste into a terminal. The icon turns into a green check for a second to confirm.

Runs the command's own built-in help (netstat /?, Get-Help Test-NetConnection, or --help on Linux/macOS) and shows it in a terminal tab — the full list of switches, straight from the tool. Available on every card, including copy-only ones.

A drop-down of vetted flag combinations for the command — ping -t (continuous, stop with Stop), ping -n 20, tracert -h 15, nslookup -type=MX, netstat -anob, whoami /groups, and so on. An input box appears when the command needs a target. Type a computer name (github.com) or an address (192.168.1.1); a red border means the value isn't valid (spaces and special characters aren't allowed). Press Enter in the box to run.

One-click chips that fill the host box with your router, your DNS server, Cloudflare's 1.1.1.1, localhost, or a host you used recently.
Orange note
Explains why a command has no run button — it changes settings, needs admin rights, is interactive, or usually isn't installed.

The terminal drawer

The dark panel pinned to the bottom of the window. It stays collapsed to a thin bar until you run something, then opens to show the output. Each run gets its own tab, so a slow command keeps going while you start another.

Tab strip
One tab per run, named after the command. Click to switch; click × to close (this also stops the command if it's still running). The active tab has a green underline.
status dot
Pulsing green: running. Solid green: finished normally. Amber: finished but reported a problem (for example, ping got no replies). Red: couldn't run at all. Gray: you stopped it.
> command · time · duration · exit 0
The line at the top of each tab: what ran, when it started, how long it has been running (it counts up live), and its exit code. exit 0 means "completed without error"; anything else means the program is reporting a failure — for ping, exit 1 simply means the host didn't reply.
find in output
On the right of that line. Type to highlight every match in the output and see the count; Enter jumps to the next match, Shift+Enter to the previous, Esc clears. Works while a command is still running.
wrap
Toggles line wrapping. Off shows long lines (like route print or wide PowerShell tables) on one line with a horizontal scroll, which keeps columns aligned. The setting is remembered.
save
Downloads the tab's output as a .txt file named after the command and time, with the command line and timestamp at the top — for attaching to a ticket or comparing later.
Table / Raw
Appears only for commands NetDeck knows how to parse. Switches between the plain text output and a sortable table (see Table view).
Stop
Ends the running command in the active tab. Use it for long ones like pathping or tracert to a host that isn't answering.
Copy
Copies the whole output of the active tab. For a playbook, it copies the step-by-step summary and the verdict.
Close all
Closes every tab at once and stops anything still running. Your history is kept.
History
Toggles the recent-runs panel on the left side of the drawer (see History).
🔔︎ notify
When switched on (the browser asks permission once), a test notification appears at once so you can see they reach the desktop, and from then on any run or playbook that finishes while the NetDeck window is not the active one — behind another window, minimized, or a different browser tab — raises a desktop notification with the result; clicking it brings NetDeck back and shows that tab. Handy for pathping and systeminfo.
link
On the right of each tab's top line: copies a link that opens this exact command with its host and variant pre-filled. Web editions only — not in the desktop app.
↕
Switches the drawer between half-height and tall.
Expand / Collapse
Shows or hides the drawer body. Collapsing doesn't stop or discard anything.

Table view

Raw command output is designed for the 1990s. For the commands where it matters, NetDeck turns it into a real table:

  • Click a column header to sort; click again to reverse. Numbers sort as numbers.
  • Filter rows… keeps only rows containing what you type — type 443 to see everything on port 443, or LISTENING to see only open ports.
  • The row count on the right shows how many rows match.
  • For netstat -ano and Get-NetTCPConnection, NetDeck adds a Process column by looking up each PID — so instead of "PID 21920 is on port 80" you see "com.docker.backend.exe is on port 80".

Commands with a table view: netstat -ano, arp -a, route print, ipconfig /all, ipconfig /displaydns, tasklist, getmac, Get-NetTCPConnection, Resolve-DnsName.

History

Every finished run is remembered — the last 30, output included — in your browser, so it survives closing the page or restarting the server. Open it with the History button.

Row
Status dot, the command, and when it ran / how long it took / its result. Click the row to reopen the output in a new tab.
↻
Runs that exact command again, with the same host and port.
Clear
Forgets everything in the history. (Close all does not do this.)

Working with results

Four tools on the output bar and in each tab turn a run into evidence you can keep, compare and hand over.

note
On the right of a run's top line (and on the bar above a playbook's steps). Opens a box for a note about this run — what you were seeing, a ticket number, what you tried. The note is saved with the run in History (a ✎ marks entries that have one; hover to read it) and goes into any report you save. It is yours alone; nothing is sent anywhere.
Compare
With a finished run in front of you, press Compare and pick an earlier run of the same command or playbook — an open tab or a History entry. NetDeck opens a new tab showing the difference line by line: lines only in the older run in red, only in the newer in green, unchanged stretches folded. For playbooks it compares the step summaries and the verdict. This is the "what changed since it worked?" question answered in one click; run ipconfig /all, route print or the network scan when things work, and compare when they do not.
Report
Saves the run in front of you as a single HTML file: title, time, your note, the output and its table for a command, the steps (with their full output in collapsible sections) and the verdict for a playbook. It opens in any browser and has a Print / save as PDF button. Anonymize is on by default: your computer's name becomes OFFICE-PC, every address is replaced consistently (private ones with 192.0.2.x, public with 203.0.113.x — so the same device keeps the same fake address throughout), and the device half of MAC addresses becomes xx-xx-xx. Well-known addresses such as 1.1.1.1 are left alone. Turn it off for a report you keep yourself.
Schedule
Runs a playbook every 5 minutes to 3 hours while NetDeck is open — Scan my network every 15 minutes, say, or Does my connection drop out? every hour. Each run opens a tab; an unchanged run replaces the previous one so tabs do not pile up. A run whose result changed — a new device, a verdict that flipped, a step that started failing — is kept, marked with "!" in its tab, counted on the ⏱ badge in the context strip, and (if you tick "notify on change") announced with a desktop notification. Schedules are remembered and resume when NetDeck is reopened; they never run while it is closed. Playbooks that need input appear in the list once you have run them, with the input you used last.

Dashboard

The third view is one screen that answers "how is the network right now?" without running anything by hand. Nothing on it is measured in a new way: every figure comes from a command or playbook check that exists elsewhere in NetDeck. The dashboard runs the quick ones itself, in a few seconds, and for the slow ones (a network scan, the DNS honesty check, the router check-up) it shows the most recent run and how old it is. That is also what makes it honest — any number can be traced back to real output: click a tile, or the run beside a row, and the command runs in the terminal drawer. The book icon in each card's corner (and beside Refresh) opens this section at that card, as it does on command and playbook cards.

Reading the dashboard

Colors. Every tile has a colored left edge, and every check row a colored dot. Green means the check passed and the figure is in a healthy range. Amber means it works but something is off — slow, weak, or worth a look. Red means it failed. Gray means not checked yet, or not applicable (Wi-Fi on a wired PC). Amber is the color to read most carefully: it is where the dashboard has an opinion and the explanation is in the small text.

Ages. "just now", "3 min ago", "2 h ago": how old a figure is. The tiles for the quick checks are as old as the last Refresh; the Router and Internet tiles update every ten seconds on their own; the playbook tiles and the Network card are as old as the last time you ran that playbook. A stale figure is not wrong, it is just old — the age is always shown so you can decide.

Units. Latencies are in ms, milliseconds, and mean a round trip: out and back. Speeds and traffic are in Mbit/s, megabits per second, the unit ISPs sell; divide by 8 for the MB/s a download dialog shows (100 Mbit/s ≈ 12.5 MB/s). Data totals are in MB or GB (bytes). Percentages of loss are "of the pings sent".

Where the numbers come from

Quick checks: ipconfig /all, ping ×4 to the router and to 1.1.1.1, nslookup example.com, a timed curl to https://example.com/, netsh wlan show interfaces, netsh advfirewall show allprofiles, and Get-CimInstance Win32_OperatingSystem — all read-only, no administrator rights. Slow checks: the Scan my network, Is my DNS honest? and Router check-up playbooks, plus any speed test, traceroute or stability monitor you run, whether from the dashboard, a command card or a playbook.

Clicking a tile runs its source: the quick tiles run their command in the terminal, the playbook tiles run the playbook again.

Refresh, and the line above the tiles

Refresh runs the quick checks again, all at the same time, in about three seconds. The line above the tiles reads, for example, Last check 18:41:25 (46 s ago) · 3.1 s · router and internet pings update every 10 s: when the quick checks last ran, how long they took, and a reminder that the two ping tiles keep updating between refreshes. The dashboard refreshes by itself when you open it if the last snapshot is more than two minutes old, and whenever a newer version of NetDeck has added a tile that the saved snapshot does not have. The snapshot is kept in this browser (or the desktop app), so the dashboard always opens with something to show.

Snapshot

Snapshot saves the whole dashboard as one HTML file — every tile and card exactly as it is on screen, with a Print button for a PDF. Tick Anonymize (on by default) to replace this computer's name, IP addresses (each real address gets the same substitute every time, so the picture stays consistent) and the device half of MAC addresses, the same way a run report does. The file needs nothing else to open, so it can go to IT or your provider as "this is what my network looked like at 18:41".

Outage log

Most connection problems hide from you: the internet drops for forty seconds at 3 a.m., or twice during a call, and by the time you run a test everything looks fine. The outage log catches those drops. Once you press Start watching, NetDeck checks the connection every 5 seconds for as long as it runs — with the window open or closed to the tray — and writes down every outage: when it started, how long it lasted, and which side of your router it happened on. That last part is what settles the usual argument: whether the fault is your internet provider's or something at home.

How it tells where the fault is

Every 5 seconds NetDeck sends two pings at once: one to your router (the default gateway, the first box your traffic reaches) and one to the internet (1.1.1.1, with 8.8.8.8 as a second opinion so one company's hiccup is not blamed on your line). A ping is a tiny "are you there?" message; the reply comes back in a few milliseconds. When the internet stops answering, what the router did at the same moment says where the break is:

Where it failedWhat NetDeck sawWhose to fix
Past your routerThe router kept answering; the internet did not. Your PC, the Wi-Fi or cable and the router were all working — the break was further out.Your internet provider: their line, their network, or the modem they supplied. (If a VPN is on, its server counts as "past the router" too.)
Between this PC and the routerNeither answered: the router itself went quiet.You: weak or crowded Wi-Fi, a bad cable, or a router that freezes or restarts on its own.
PC disconnectedThis PC had no router address at all — it had dropped off the network.You: Wi-Fi disconnecting, a cable coming out, or Windows switching the adapter off to save power.
UnclearThe router has never answered a ping (some are set up to ignore them), so there is nothing to compare against.Unknown. Run Does my connection drop out? during a bad spell for a closer look.

An outage is no reply from the internet for about 10 seconds or longer — two checks in a row at the usual 5-second pace, or five while the Network sensors card or mini monitor has it checking every 2 seconds. Anything shorter is a blip: it is counted but not listed, because one lost ping now and then is normal on any network. Start and end times are accurate to about 5 seconds.

Things to know

  • It only sees what happens while NetDeck runs. Closing the window keeps it going in the tray; Quit NetDeck stops it. Turn on Start with Windows — the button on this card, or the tray menu — and NetDeck opens hidden in the tray each time you sign in, so watching resumes by itself after a restart. The local-server edition watches while its window is open.
  • Sleep is not an outage. Time the PC spends asleep or off shows as "not watching", never as downtime, and the first minute after NetDeck starts or the PC wakes is ignored, because reconnecting takes a few seconds.
  • "Past your router" includes everything beyond it. With double NAT — a provider's box in front of your own router — an outage in that box shows as past your router, which is right: it is the provider's equipment.
  • The cost is tiny. About two small pings every 5 seconds — a few kilobytes an hour. Nothing else is sent anywhere.
  • The log stays on this PC, in outage-log.json: %APPDATA%\com.netdeck.desktop\ for the desktop app, or next to server.js for the local-server edition.
Talking to your provider

Support lines usually test the line while you are on the phone, find nothing and close the ticket. A report changes that: give them the exact times and lengths of the outages, and ask them to check their records for your line at those moments. If every outage is "past your router" while the PC was on a cable to the router, the fault is theirs to find. If they are "between this PC and the router", start with Wi-Fi: move closer to the router, or try a cable, and watch whether the outages stop.

An IPv4 address is a 32-bit number. People write it as four 8-bit pieces called octets, each shown in decimal (0 to 255) and separated by dots: 192.168.1.100. Computers see only the bits. Each octet converts to binary using the place values 128, 64, 32, 16, 8, 4, 2 and 1 — a bit is 1 when that value is part of the number:

Network part and host part. Every address has two parts. The first bits say which network the device is on — like a street name; the rest say which device on that network — like the house number. Devices on the same network talk to each other directly. To reach anything on another network they send the traffic to their gateway, the router, which passes it on.

The subnet mask says where the split is. It is another 32-bit number: ones over the network part, zeros over the host part — always a single run of ones followed by zeros. To find the network an address belongs to, a device combines the address and the mask bit by bit with AND: a bit survives only where the mask has a one.

CIDR notation writes the mask as the number of ones: 255.255.255.192 has 26, so the network is 192.168.1.64/26 (Classless Inter-Domain Routing). The remaining 32 − 26 = 6 bits are the host part, which gives 26 = 64 addresses.

Two addresses in every subnet are special. The first (all host bits 0) is the network address: it names the subnet and no device uses it. The last (all host bits 1) is the broadcast address: a packet sent there goes to every device in the subnet. So a /26 has 64 − 2 = 62 usable addresses, here 192.168.1.65 to 192.168.1.126. Two exceptions: a /31 has no broadcast and both addresses are usable, for a link between two routers (RFC 3021), and a /32 is a single address.

How IPv6 addresses work

Why IPv6 exists. IPv4 has 32-bit addresses — about 4.3 billion of them, fewer than the people on Earth, let alone their phones, laptops and TVs. The last free blocks were handed out in 2011. NAT stretched IPv4 by hiding a whole home behind one public address, but at the cost of devices that cannot be reached directly. IPv6 fixes the shortage for good: its addresses are 128 bits, about 340 undecillion (3.4 × 1038) of them. Most networks today run both side by side (dual stack); your PC very likely has IPv6 addresses already — ipconfig lists them.

Reading an address

128 bits written in binary would be unreadable, so IPv6 uses hexadecimal: each hex digit (0–9, a–f) stands for 4 bits. The 32 digits are written in eight groups of four — each group is 16 bits, sometimes called a hextet — separated by colons:

2001:0db8:abcd:0012:0000:0000:0000:0001

Two rules make it shorter, applied in this order:

  1. Drop leading zeros in each group. 0db8 becomes db8, 0012 becomes 12, 0000 becomes 0, 0001 becomes 1: 2001:db8:abcd:12:0:0:0:1. Only leading zeros go — 12 can never be written for 1200.
  2. Replace one run of all-zero groups with ::. The three zero groups collapse: 2001:db8:abcd:12::1. You can do this only once in an address. To expand it again, count the groups you can see (five here) — the :: stands for however many are missing to make eight (three). With two :: the reader could not tell how to share out the missing groups.

Both forms are the same address. Because one address can be written many ways, RFC 5952 fixes one canonical form — lower case, leading zeros dropped, the longest zero run compressed (the first, if two tie), a single zero group left as 0. Always compare, search logs and write documentation in that form; the calculator's Compressed row gives it to you.

As in IPv4, a prefix length says how many bits from the left name the network; the rest name the device on it. 2001:db8:abcd:12::1/64 means the first 64 bits are the network. A typical global address divides into three parts:

Why nearly every subnet is a /64

In IPv4 you size a subnet to fit its devices. In IPv6 you don't: every ordinary subnet — a home LAN, an office VLAN, a guest Wi-Fi — is a /64, 18,446,744,073,709,551,616 addresses. That is not waste; it is what lets devices pick their own 64-bit interface IDs without a server and without ever colliding. How a device gets its addresses

On most networks nobody hands out IPv6 addresses one by one. The router sends out a Router Advertisement saying "this network is 2001:db8:abcd:12::/64, and I am the way out". Each device takes that prefix and adds an interface ID it chooses itself — SLAAC, stateless address autoconfiguration. Some networks use DHCPv6 instead or as well, much like DHCP in IPv4. The router's own address, the default gateway, is usually its link-local fe80:: address.

That is why ipconfig shows several IPv6 addresses for one adapter, and why that is normal:

  • Link-local (fe80::…) — every IPv6 interface makes one for itself, even with no router. It works only on the local network segment and is used for things like finding the router and neighbors.
  • IPv6 Address — a stable global address, the same each time the PC joins this network, used for incoming connections.
  • Temporary IPv6 Address — a random one, replaced every day or so, used for outgoing connections so websites cannot follow the PC by its address.

Where the interface ID comes from

Older systems built the interface ID from the network card's MAC address, a method called EUI-64. Take the 48-bit MAC, split it in half, put ff:fe in the middle, and flip the seventh bit of the first byte (the "universal/local" bit):

MAC address00-00-5E-00-53-01
Split and insert ff:fe00:00:5e:ff:fe:00:53:01
Flip the U/L bit (00 → 02)0200:5eff:fe00:5301
Interface ID0200:5eff:fe00:5301

The problem: the MAC — and so the maker of the hardware — shows in every address, and the device can be recognized on any network it joins. Windows, macOS, iOS, Android and modern Linux therefore use random interface IDs instead: temporary ones for outgoing traffic (RFC 4941) and a stable random one per network (RFC 7217). You still meet EUI-64 on routers, printers and older embedded devices; ff:fe in the middle of the last half is the giveaway, and the IPv6 tool spots it and recovers the MAC.

What is gone from IPv4, and what replaces it

  • No broadcast. Messages for "everyone on this network" use multicast groups instead — ff02::1 is all devices on the link, ff02::2 all routers — so devices only hear what they joined.
  • No ARP. Neighbor Discovery finds the MAC address behind an IPv6 address (netsh interface ipv6 show neighbors lists what it found).
  • No NAT needed. Every device can have a public address, so the firewall — in the router and on the PC — is what keeps unwanted traffic out. Having a global address does not mean being reachable; a home router blocks incoming IPv6 connections by default.
  • Private addresses still exist. Unique local addresses (fd…) are for networks that should never be routed to the internet, like 192.168.x.x in IPv4 — but they are chosen at random, so two networks joined later rarely clash.

MAC addresses in brief

A MAC address is the 48-bit hardware address of a network adapter, written as six pairs of hex digits: 00-00-5E-00-53-01 (Windows uses dashes, Linux and macOS colons, Cisco groups of four: 0000.5e00.5301). It is used only on the local network — routers do not pass it on. The first three bytes are the OUI, the number the IEEE assigned to the manufacturer, which is how NetDeck names who made a device. Two bits in the first byte carry flags: the lowest (I/G) is 1 for a group (multicast) address, and the next (U/L) is 1 for a locally administered address — one made up by software rather than burned in. Phones, tablets and recent laptops use such random addresses on Wi-Fi so that networks cannot track them, which is why they show up with no manufacturer.

Transfer time

Throughput & latency

TCP throughput

Why a fast line can still give a slow download. A single TCP connection is held back by whichever of three limits is lowest:

  • The line speed.
  • The window limit = window ÷ round-trip time. TCP sends one window of data and then waits for it to be acknowledged, so across a long distance it spends most of its time waiting. A 64 KB window over 100 ms caps a connection at about 5 Mbit/s whatever the line; Windows grows its window automatically up to 16 MB.
  • The loss limit — the Mathis formula: (segment size ÷ round-trip time) × 1.22 ÷ √(loss rate). TCP halves its speed every time a packet is lost, so even 0.1% loss over 40 ms holds one connection to about 11 Mbit/s.

The bandwidth-delay product — line speed × round-trip time — is how much data must be in flight to keep the line full, and so how big the window must be. Parallel streams shows why download managers and speed tests open several connections at once: each has its own window and its own loss penalty. Latency budget

Where the milliseconds of a round trip come from:

  • Propagation — distance ÷ the speed of the signal. Light in fiber travels at about two-thirds of its speed in a vacuum, roughly 200 km per millisecond. Cables do not run in straight lines, so the route factor (1.3 by default) stretches the distance.
  • Serialization — the time to clock a packet onto each link: size ÷ link speed. 1,500 bytes take 0.12 ms at 100 Mbit/s but 12 ms at 1 Mbit/s.
  • Processing in each router, usually tiny, and queuing — time waiting behind other packets, near zero on an idle line and hundreds of milliseconds under bufferbloat.

Presets fill in typical paths, including a geostationary satellite (36,000 km up and down again, so about 480 ms round trip before anything else) and a low-orbit one. The note at the bottom states the physical floor: no technology can beat the speed of light over that distance.

Can't reach the internet?

The one to start with when "the internet is down". It walks the chain outward from your computer and stops at the first broken link:

  1. Check your adapter — does the adapter you're actually using (the one in the context strip) have a real address and a gateway? It ignores virtual adapters from Docker, Hyper-V or a VPN, which otherwise hide a dead connection. A failure here stops the run (cable / Wi-Fi / DHCP problem). It also warns if a second adapter has a default route but no valid address, which can quietly capture your traffic.
  2. Ping the router — does it answer, and quickly? Over 50 ms or any lost packets is flagged: on Wi-Fi that means weak signal or interference.
  3. Ping the internet at 1.1.1.1 — does anything past the router answer?
  4. TCP to 1.1.1.1 (only if that ping failed) — many office networks block ping, so before blaming your provider it tries a real connection. If this works, you're online and ping is simply blocked.
  5. Resolve example.com — do names still work? (fail → DNS problem; the verdict offers to run the DNS playbook)
  6. Look for a sign-in portal — fetches Microsoft's connectivity test page. A redirect or a different page means hotel/café/guest Wi-Fi is waiting for you to sign in.
  7. HTTPS to example.com — can you actually open a secure connection? (fail → firewall, proxy or security software)

Is a port open on a host?

Give it a host and a port (say github.com and 443). It resolves the name, pings the host, then tries the port. The point is telling apart situations that look identical in a browser:

  • The name doesn't exist — the run stops there.
  • Refused — the connection is rejected within a few seconds. The machine is up and said "no": nothing is listening on that port (service stopped, or it's on a different port).
  • Filtered — no response at all until the ~20-second timeout. A firewall is silently dropping the connection.
  • Nothing answers — neither ping nor the port. Only then does it run a quick route trace to show where the path stops: inside your own network, in your provider's, or beyond.

Is DNS healthy?

Looks up the same name through your configured DNS server, your second configured server if you have one (a dead backup server causes random multi-second stalls), then Cloudflare (1.1.1.1) and Google (8.8.8.8) — timing each answer. If yours fails and the public ones work, your router or provider's DNS is the culprit and the verdict tells you to switch. If they all fail, it's not DNS at all — you have no connectivity, and the verdict offers the internet playbook.

The last step asks for a name that cannot exist (it ends in .invalid). An honest resolver says "no such name"; if an address comes back, something — your provider's search page, a captive portal, a filtering product — is rewriting DNS answers. A lookup that succeeds only after a first attempt timed out is reported as slow, not broken.

Scan my network

Two steps now. First it asks devices to announce themselves over mDNS/Bonjour and UPnP, which is how TVs, speakers, printers, Apple and Google devices give their real names. Then it pings every address in your subnet at once and reads the ARP table. The table gains three things: the Name column fills from what devices said about themselves, a Seen column says when NetDeck first saw each device (NEW means never before), and every row has a probe button that runs the port probe on that address to ask what it is. The verdict adds what changed since the previous scan — new devices, devices that have gone, and devices that changed address — because NetDeck now remembers each scan (in this browser or app only; nothing leaves the PC). A new device turns the verdict amber so it is not missed.

NetDeck's IP scanner: it finds every device on your network, not just the ones this PC has talked to. There is nothing to type — it works out your subnet from your own address, pings all of its addresses at the same time (so 254 addresses take about six seconds, not four minutes), then reads the ARP table the sweep has just filled. That second step matters: phones, TVs and smart-home gadgets often ignore ping, but they cannot avoid answering ARP, so they still show up — marked no reply in the Ping column.

Press table for the full list: IP address, name (when the network can supply one — on home networks it usually can't), MAC address, manufacturer, whether it answered ping, and a note marking this PC and the router. Sort by Manufacturer to group things: five Wyze cameras, three eero units and so on. Two values in that column deserve explanation:

  • private address (randomized) — phones, tablets and recent laptops invent a random MAC address for each Wi-Fi network, for privacy. It belongs to no manufacturer, so it can't be identified this way. Usually these are your family's phones.
  • blank — the prefix is not in the IEEE registry NetDeck carries (the official list of every manufacturer's address blocks, about 54,000 entries, bundled with the app). That is rare for real hardware: it usually means a virtual adapter, a device faking its address, or a very new assignment — the registry is refreshed with each NetDeck release.

Anything you can't account for is worth tracking down; your router's own client list usually shows a name for each address. What it will not do: it only ever scans the private subnet this PC is on, never more than 254 addresses, and refuses to run on a public address — it's a "what's on my network" tool, not a general scanner. Reply times aren't shown, because pinging 254 addresses at once makes them meaningless; use ping on one device for that.

Who's on my network?

Pings your router to freshen the cache, then reads the ARP cache (every device your computer has recently exchanged packets with), counting real devices on your network and ignoring broadcast and multicast entries. Press table on that step to see each device's IP and MAC address. The cache only knows devices you've exchanged traffic with, so quiet ones can be missing.

A website won't load

The most common complaint, and the hardest to untangle by hand. Give it the site (you can paste a whole address — it keeps just the host). It resolves the name with your DNS and with a public one, connects to port 443, asks for the page headers, times each phase of a real request, and — only if something failed — loads a known-good control site so it can tell "it's them" from "it's you". Possible verdicts:

  • Your DNS can't resolve it but public DNS can — stale cache, filtering, or a blocked name; offers the DNS playbook and the flush command.
  • The name doesn't exist — a typo, or the domain lapsed.
  • The site refuses or drops connections while the control site loads — it's at their end (or they are blocking you).
  • Nothing loads, control included — it's your connection; offers the internet playbook.
  • The secure connection fails — certificate or TLS error. Check this PC's clock first, then security software or a proxy.
  • HTTP 5xx — their server is erroring. 403 / 404 — the site is up; that page or your access is the issue.
  • It loads, slowly — and says which phase ate the time: looking up the name, reaching the server, setting up encryption, waiting for the server to build the page, or downloading.

Why is everything slow?

Twenty pings to your router and twenty to the internet — reporting average, worst case, jitter (how much the delay wobbles) and loss — then a timed DNS lookup and a timed web request, and the Wi-Fi link if you're on wireless. Takes about a minute. The logic is simple: if the numbers to your router are bad (a healthy link is 1–5 ms with almost no jitter), the problem is between this PC and the router — Wi-Fi signal, interference, a cable. If the router is clean but the internet numbers are bad, it's your provider or a saturated connection, and the verdict offers to trace the path. If both are clean it checks whether DNS or the web server was the slow part.

Does my connection drop out?

Where does the path break?

Runs a route trace (up to 20 hops) and reads it for you. It reports whether the destination was actually reached — tracert prints "Trace complete" even when the last hops never answered — where replies stop, and where latency steps up and stays up (one router replying slowly is normal and ignored). Each hop is labeled as your network, your provider's access network, or the internet, so "hop 2" becomes "the link to your provider". Press table for the hop list. Some hosts never answer traces; if the site works in a browser, a trace that goes quiet near the end means only that.

What is this PC exposing?

Lists every TCP port this machine is listening on with the program behind it, split into reachable from the network (listening on all addresses) and local only (127.0.0.1, invisible to other machines). It flags remote-access and database services — Remote Desktop, VNC, Telnet, FTP, SQL Server, MySQL, PostgreSQL, Redis, MongoDB, the Docker API — which are the ones worth being sure about, and checks that Windows Firewall is on for every profile. Ports 135, 139 and 445 are standard Windows services, and the block of high ports (49152 and up) are Windows' own; both are summarized rather than listed one by one. "Reachable" means a program is listening; whether the firewall lets outsiders in depends on its rules.

Routing & adapter sanity

For "it works on Wi-Fi until I plug the cable in", half-connected VPNs, and connections that die for no visible reason. It reads the routing table for default routes — the "send everything else this way" rules. One is normal. Several means adapters are competing, and the lowest metric wins; the verdict lists them with the winner marked ▶. The dangerous case is an adapter that holds a default route but has no valid address (cable plugged in, DHCP failed): if it wins, your traffic goes nowhere. It also lists which DNS servers each adapter uses — a VPN adapter often takes DNS priority, which is why lookups may go to a server you don't recognize.

Did my DNS change propagate?

For when you've changed a DNS record and want to know who sees it yet. It finds the domain's authoritative nameservers (looking in the parent zone if you gave a host like www.example.com), asks them directly — that's the truth — and compares the answers from your resolver, Cloudflare, Google and Quad9. Resolvers that differ are serving a cached copy that updates when the old record's TTL expires; nothing to fix, just wait (or flush your own cache). If the two authoritative servers disagree with each other, the zone hasn't synchronised at your DNS host, which is worth fixing first.

Large sites rotate or geo-balance their addresses, so every query gets a different answer. The playbook detects this by asking the same authoritative server twice; when it sees rotation it compares network ranges instead of exact addresses, and says so.

Wi-Fi health

Reads your wireless link — signal strength, band (2.4 or 5 GHz), radio mode, link rate — then surveys nearby access points to count how many strong ones share or overlap your channel, and sends twenty pings to the router to see how steady the link really is. Flags weak signal (under 55%), the crowded 2.4 GHz band, old radio modes and low link rates; on 2.4 GHz it suggests the quietest of channels 1, 6 and 11. On Windows 11 the first two steps need Location services on (or an administrator shell); without that the ping test still tells you whether the link is steady.

Can I reach that service?

Give it one host. It checks the name and ping, then tries the common service ports in a single run — HTTPS 443, HTTP 80, SSH 22, Remote Desktop 3389, SMB file sharing 445, SQL Server 1433 — and lists each as open, refused (the machine is up, nothing is listening) or filtered (a firewall drops it). If the host answers neither ping nor the web ports it stops early rather than waiting out every timeout. This is a small port sweep: use it on machines you're responsible for.

MTU check — "some sites hang"

Every network path has a largest packet size, its MTU (Maximum Transmission Unit) — normally 1500 bytes; less over PPPoE, VPNs and tunnels. It sends pings marked "don't fragment" at decreasing sizes and stops at the first that gets through; that size plus 28 bytes of headers is your path MTU. A smaller MTU is fine as long as the "packet too big" messages reach you. When a firewall blocks them, small transfers work and large ones silently stall: pages half-load, uploads hang, VPNs feel flaky. The verdict gives the number to set on the adapter or VPN if you have those symptoms.

Email delivery check

Give it a domain (the part after the @). It looks up the MX records (which servers receive its mail), checks for an SPF record (which servers may send as this domain) and a DMARC record (what receivers should do with forgeries) — missing ones are the usual reason legitimate mail lands in spam — and tries port 25 on the first mail server. Expect that last step to fail on home and most office connections: providers block outbound port 25, and mail programs use 587 or 465 instead. The verdict says so rather than calling it a fault.

PC health snapshot

IPv6 check

Most networks are fine either with working IPv6 or with none. Can't see the other PC / shared folder

The most common Windows networking complaint, and one with a short list of causes that the error messages never name. Type the other PC's name (or address) and the playbook checks both ends in the order the failures actually happen.

Step 1 — this PC. Windows keeps a network profile for every connection: Private (home or office: look for other devices, let them in) or Public (café: hide, refuse everything). A Wi-Fi network that was joined once as Public stays Public, and on a Public network discovery and sharing are off in both directions — you cannot see them and they cannot see you. The step reads the profile of every connected adapter, then the services that sharing depends on (Workstation to reach shares, Server to offer them, Function Discovery to appear in Network view, DNS Client to answer names), then the inbound File and Printer Sharing firewall rules for the profile you are on, and finally the SMB client setting that blocks password-less shares. It reports two things separately: whether this PC can reach others, and whether others can reach it — most people only need the first.

Step 2 — the name. Windows resolves a PC name three ways, one after another, and the playbook tries each separately so you can see which one knows it: your DNS server (a home router usually does not), LLMNR/NetBIOS (a shout on the local network: "who is OFFICE-PC?"), and mDNS (OFFICE-PC.local). All three fail when the name is misspelt, when the two PCs are on different subnets, or when the Wi-Fi keeps its clients apart (a guest network, or "client isolation" — common on hotel and office Wi-Fi). If a name fails but the address works, the name is the only problem.

Steps 3 and 4 — the other PC. A ping, then a connection to port 445, which is what \\PC\share actually opens. The two together separate the cases: nothing answers (it is off, asleep, elsewhere, or itself set to Public); ping answers but 445 is refused (its Server service is off — sharing disabled); ping answers but 445 is ignored (its firewall drops the connection — again usually the Public profile). The verdict names the setting on the right PC.

What it cannot see. Permissions. If the share opens but Windows asks for a user name or says "You can't access this shared folder", the network is fine: the share needs an account that exists on that PC, because Windows blocks password-less guest shares by default (step 1 tells you whether this PC allows them). Old NAS boxes that only speak SMB1 are the other case; NetDeck cannot enable SMB1 and you should think twice before doing so.

Printer won't print

Printing fails at one of four places, and Windows tells you almost nothing about which: the spooler on this PC, the queue, the network path to the printer, or the printer itself. The playbook needs no input — it finds your network printer among the printers installed on this PC (the default one if it is a network printer, otherwise the first).

Step 1 — this PC. The Print Spooler service (when it is stopped, nothing prints and every printer shows as unavailable), every installed printer with its kind — network with an address, WSD (found by broadcast, with no fixed address), USB, shared from another PC, or virtual (PDF, OneNote) — the status Windows shows for it, and the number of jobs waiting and stuck. A stuck job at the head of a queue blocks everything behind it; canceling it is often the whole fix.

Steps 2 to 6 — the printer. A ping to its address, then its printing ports: 9100 (raw, also called JetDirect — what most Windows drivers use), 631 (IPP, what AirPrint and modern drivers use), 515 (LPR, older), and 80 for the printer's own web page. A printer that answers ping but opens none of the ports is awake but not accepting work — starting up, in an error state, or with network printing switched off. One that answers on a different port from the one Windows is configured to use is a port-configuration problem, and the verdict says which protocol to switch to.

The usual culprit. Home routers hand addresses out by DHCP, and after a reboot a printer can come back with a different one while Windows still points at the old. If the ping fails, the playbook looks in the scan log — the record Scan my network keeps — for a device whose name matches the printer's, and if it finds one at another address it says so. The lasting fix is a fixed address for the printer, set in the router (a DHCP reservation) rather than on the printer. WSD printers are the other version of the same problem: Windows finds them by broadcast, which breaks when the printer moves network or sleeps deeply; adding the printer again by IP address gives a connection that survives.

Is my VPN really working?

A VPN app shows "Connected" when its tunnel is up. That is not the same as your traffic going through it, and the difference is invisible without looking at the route table. This playbook looks.

Step 1 — the route. Every packet not addressed to your own network follows the default route, and when several exist Windows takes the one with the lowest metric. A working privacy VPN puts its adapter's default route first: a full tunnel. A split tunnel leaves the ordinary default route in charge and adds only specific routes for the VPN — what corporate VPNs do on purpose (only work addresses go through) and what a privacy VPN should never do. The step lists VPN-looking adapters (WireGuard, OpenVPN, Tailscale, the built-in Windows VPN types and most commercial apps) with their address, MTU and DNS server, then the default routes in metric order, and says which kind of tunnel you have.

Step 2 — the address the internet sees. A request to Cloudflare's trace endpoint returns the public address and country your connection appears from. Through a full tunnel that is the VPN server's, not yours.

Step 3 — DNS leak. The tunnel can carry your traffic while your name lookups still go to the ISP's resolver, which then sees every site you visit. This step is the same egress test as Is my DNS honest?, read with the VPN in mind; the fix is the VPN's own DNS server (most apps have a setting) or an encrypted resolver.

Steps 4 and 5 — MTU. A VPN wraps every packet in another, so fewer bytes fit: a tunnel adapter's MTU is typically 1400 to 1420 instead of 1500. When a packet is too big and the path refuses to say so, connections stall — the classic "VPN connects, most things work, but some sites hang and uploads freeze". The playbook sends don't-fragment pings of 1372 bytes and, if those fail, 1272, through the tunnel; the verdict gives the MTU to set and the command that sets it.

Will my video calls be OK?

A call needs something different from a download: not much bandwidth, but a steady path, in both directions, over UDP. This playbook measures each of those.

Steps 1 and 2 — jitter and loss. Twenty pings to the router and twenty to the internet. The average matters less than the jitter (how much the delay varies from ping to ping) and any lost replies: a call has to play audio at a steady rate, so variation turns into stutter and loss into gaps. Jitter under 10 ms on the local link and under 30 ms beyond it is comfortable. High jitter to the router with a clean internet leg means the Wi-Fi is the problem.

Step 3 — Wi-Fi. Signal, band, radio mode and link rate, when you are on Wi-Fi. A weak signal or a crowded 2.4 GHz channel shows up as jitter in step 1; a cable for the call is the single biggest improvement.

Step 4 — NAT type. Calls try to connect the two ends directly. To do that, each side asks a public STUN server "what address and port do you see me as?" and tells the other side. The playbook asks two servers from the same local port: if both see the same public port, your router keeps a stable mapping (endpoint-independent, or "cone" NAT) and direct connections work; if each sees a different port (symmetric NAT), the other side can never guess the right one and the call falls back to a relay, adding delay — or fails. No answer at all means UDP is blocked outbound, which is the worst case for calls.

Step 5 — speed and bufferbloat. The speed test, read for calls: upload matters more than download (HD video wants about 3 Mbit/s up, a group call more), and the bufferbloat grade tells you what happens when someone else in the house starts a download — a router that queues too much lets the latency climb by hundreds of milliseconds under load, and the call stutters until the download ends. Grade A or B is fine; C or D is fixed by a router with smart queue management (SQM / "QoS"), not by a faster line.

Am I behind double NAT or CGNAT?

NAT (network address translation) is what lets every device in your home share one public address: your router rewrites the addresses on the way out and back. Once is normal. Twice breaks things — port forwarding, remote access, game consoles reporting "strict NAT", some VPN and VoIP setups — and it happens two ways.

Double NAT is two routers in a row, typically the ISP's modem/router with your own router behind it. Your router forwards a port to your PC faithfully, but the outer router knows nothing about it and drops the connection. Carrier-grade NAT (CGNAT) is the ISP doing the second translation inside its own network, sharing one public address between many customers; your router's "WAN address" is then a special range, 100.64.0.0/10, and nothing you forward is reachable from outside. Mobile and satellite connections almost always use it, and cable and fibre ISPs increasingly do.

Step 1 — the first hops. A short trace to 1.1.1.1 and a count of the private routers on the way out: one (yours) is normal, two in a row is double NAT, and a hop in the 100.64 range is CGNAT.

Step 2 — the router's own view. Over UPnP, the router is asked for its internet-side address. A private address there (10.x, 192.168.x, 172.16–31.x) means another router in front of it; a 100.64 address means CGNAT; a public address means it is directly on the internet. Routers with UPnP off cannot be asked, and the verdict then rests on the other two steps.

Step 3 — the address the internet sees. If the router's WAN address is public but differs from what the internet sees, something is translating in between.

Fixes. Double NAT: put the outer device into bridge mode so only your router routes (the usual answer for an ISP modem/router), or add your router's WAN address to the outer router's DMZ, or forward the same ports on both. CGNAT: there is nothing to change on your side — ask the ISP for a public address (some sell it as a static IP), use IPv6 where the service supports it, or reach home devices through an overlay service (Tailscale, Cloudflare Tunnel) that needs no forwarding.

Can't Remote Desktop to this PC

Remote Desktop has a client side and a host side, and the host side is where it goes wrong: five separate things have to be on, on the PC you are trying to reach, and Windows reports all failures with the same "can't connect" message. Run this playbook on the PC you want to reach.

Step 1 — the host, in order. First the edition: Home editions of Windows can connect out but cannot accept Remote Desktop at all, and no setting changes that. Then the Remote Desktop switch (Settings › System › Remote Desktop), which is read from the registry without changing it. Then the Remote Desktop Services service, then whether anything is actually listening on the port (3389 unless it has been changed — the playbook reads the configured port). Then the firewall: the built-in "Remote Desktop" rules exist on every PC but are only enabled when the feature is turned on, and they apply per network profile — a PC on a Public network drops the connection even with everything else right. Finally who may connect: administrators always, plus the members of the Remote Desktop Users group; the step says which you are.

Step 2 — a real connection. When the settings look right, the playbook connects to this PC's own port. A failure there, with everything above in order, points at a third-party firewall or security suite standing in front of Windows'.

The verdict names the first thing that is off and where to turn it on, then tells you what to type on the other PC (this PC's name and address, and which account). Two things it cannot check: that the other PC can reach this address at all (same network, or a VPN — Remote Desktop should never be exposed to the internet directly), and that this PC is awake: a sleeping PC accepts nothing, and Settings › System › Power decides that.

STUN — NAT type and public address PS runnable

The words first. NAT is Network Address Translation: your router gives every device at home a private address (192.168.x.x) and shares one public address between them, rewriting each packet's address and port on the way out and remembering the mapping so replies find their way back in. UDP is the User Datagram Protocol: the lightweight way of sending packets, with no connection set up first and no retransmission — what voice, video and games use, because a late packet is worth less than no packet. STUN is Session Traversal Utilities for NAT: a tiny protocol whose main job is answering one question for a device behind NAT — "what address and port does the outside world see me as?"

Why it matters. A video call or a game tries to connect the two ends directly. Each side asks a public STUN server what its public address and port are, and tells the other side, which then sends packets there. That only works if the router keeps using the same public port for that device no matter who it talks to. Some routers do (an endpoint-independent, or "cone", NAT); some hand out a fresh port for every destination (a symmetric NAT), so the port the STUN server saw is useless to anyone else, the direct connection cannot be made, and the call falls back to a relay server in the middle — more delay, sometimes a failed call.

What this command does. It opens one UDP port on this PC and sends one STUN binding request from it to each of two public STUN servers (Google's and Cloudflare's). Each replies with the public address and port it saw. Same address and port from both: endpoint-independent NAT — the good case, and if the port also matches the local one there is no NAT at all, or a port-preserving one. Different ports: symmetric NAT. No reply from either: outbound UDP is blocked on this network, which is the worst case for calls. Two 20-byte packets leave this PC; they carry a random transaction number and nothing else. Used by Will my video calls be OK?.

Glossary

IP address
A device's number on a network, like 192.168.1.45. Addresses starting with 10., 172.16–31. or 192.168. are private (only meaningful inside your network); anything else is a public internet address.
MAC address
The hardware serial number of a network card, like a4-6b-b6-12-34-56. Fixed for life; only used within your local network.
MTU
Maximum Transmission Unit — the largest packet, in bytes, a connection carries in one piece. 1500 on ordinary Ethernet and Wi-Fi; smaller over VPNs and PPPoE. When a path's MTU is lower than your PC assumes, big packets vanish and some sites load partway then hang.
CIDR
Classless Inter-Domain Routing — writing a network as an address and the number of network bits, like 192.168.1.0/24, instead of with a class. See How IP addresses work.
Octet
Eight bits — one of the four numbers (0–255) in an IPv4 address.
Subnet
A block of addresses that share their network bits; devices in one subnet reach each other directly, anything else goes through a router. See Subnetting, step by step.
Broadcast address
The last address of an IPv4 subnet; a packet sent to it reaches every device in the subnet.
Wildcard mask
A subnet mask inverted (0.0.0.63 for 255.255.255.192), used by router access lists and OSPF.
dBm / RSSI
Signal strength in decibels relative to one milliwatt — negative numbers, closer to zero is stronger; −67 dBm is the usual target for Wi-Fi calls. RSSI is the received signal strength a device reports.
NAT
Network Address Translation — how a router lets every device on a private network share one public address: it rewrites the address and port on each packet going out and keeps a table so replies come back to the right device. One NAT (your router) is normal; a second one in front of it (double NAT) or one inside the ISP (carrier-grade NAT) breaks port forwarding and some games — see the double NAT playbook. Routers differ in how they map ports, which is what the STUN test classifies.
STUN
Session Traversal Utilities for NAT — a small protocol a device behind NAT uses to ask a public server "what address and port do you see me as?". Video calls and games rely on it to connect two ends directly; NetDeck uses it to tell an endpoint-independent NAT (direct connections work) from a symmetric one (they fall back to relays).
UDP
User Datagram Protocol — the other transport next to TCP. It sends packets without setting up a connection and without retransmitting lost ones, which makes it cheap and fast: DNS lookups, voice, video and most games use it. A network that blocks outbound UDP breaks calls even though web pages (TCP) load fine.
Gateway / router
The device that forwards traffic between your local network and the internet. Its address is the "Default Gateway" in ipconfig.
DNS
Domain Name System — the service that converts names (github.com) into IP addresses. When DNS is down, "the internet is down" even though the connection is fine.
DHCP
The service (usually on the router) that hands out IP addresses automatically. A "lease" is the address you were given and how long you may keep it.
APIPA / 169.254.x.x
The made-up address Windows assigns itself when DHCP doesn't answer. Seeing it means "I'm not really connected".
Subnet mask
Defines which addresses count as "local". With 255.255.255.0, everything sharing your first three numbers is on your network; anything else goes via the gateway.
Port
A numbered door on a computer, 1–65535, each used by one program. Web is 80/443, SSH 22, Remote Desktop 3389. "Listening" means a program is waiting at that door.
TCP / UDP
The two ways to send data. TCP checks everything arrived (web, email, file transfer); UDP just sends and hopes (video, DNS lookups, games).
Latency / ms
How long a packet takes to get there and back, in milliseconds. Lower is better; under 20 ms feels instant.
Packet loss
Percentage of packets that never arrived. Anything above 1–2% makes calls choppy and pages stall.
TTL
Time To Live. In ping, roughly how many routers the reply passed through (starts at 64 or 128 and counts down). In DNS, how many seconds an answer may be cached.
ARP
Address Resolution Protocol — how devices on the same network learn each other's MAC addresses. The "ARP cache" is the resulting IP→MAC list.
PID
Process ID — the number Windows gives each running program. netstat shows PIDs; tasklist turns them into names.
Localhost / 127.0.0.1
Your own computer, from its own point of view. Pinging it tests only that networking software is alive, not any connection.
Exit code
The number a program reports when it finishes. 0 means success; anything else is a program-specific error. NetDeck shows it at the top of each tab.
Elevated / admin
A program started with "Run as administrator", after Windows' permission prompt. Some commands (netstat -b, arp -d, sfc) only work that way. Being logged in as an administrator is not the same thing: programs still start un-elevated until you approve that prompt.
NetBIOS
The old Windows naming system behind file sharing and \\COMPUTER\share paths. nbtstat speaks it.
